## Diagnóstico (causa raíz real, no hipótesis)

Se reprodujo el bug ejecutando el `jsCode` real del nodo dentro de un `vm.createContext()` (el mismo mecanismo que usa `scripts/test-commercial-baseline.mjs` para aislar los nodos de n8n) contra el fixture real. Resultado: `dominios_unicos: 0` reproducido de forma determinista.

Causa raíz: `getDomain(url)` usaba `new URL(url).hostname`. El global `URL` **no existe** dentro de un `vm.createContext(Object.create(null))` (contexto JS aislado sin globals de Node), por lo que `new URL(...)` lanza `ReferenceError`, capturado silenciosamente por el `catch` de la función, que devuelve `null` para **todas** las URLs sin excepción. El nodo Code de n8n corre en un sandbox equivalente (sin exponer `URL` como global salvo que se habilite explícitamente el modo "Node.js built-ins"), lo que explica que el mismo comportamiento se haya observado también en la evidencia real capturada en el fixture (`dominios_unicos: 0` con 20 `resultados_con_url`). El workflow hermano `RHIA - Investigación Empresa` (`docs/baseline/n8n/workflows/j4maQyGj457W4yFs.json`, nodo `Code in JavaScript1`, función `obtenerDominio`) ya resolvía esto correctamente con una regex, sin depender de `URL`.

### 4. Health score por engine — implementado y probado

Nuevo paquete `packages/search-health` (`@rhia/search-health`, mismo patrón
que `packages/outreach-policy`: `src/index.ts` + `src/index.test.ts` +
`package.json` + `tsconfig.json`, sin dependencias):

- `computeEngineHealthScores(events, options)`: score 0..1 por engine sobre
  una ventana temporal (`windowDays`, default 14 días) con **decaimiento
  exponencial** (`halfLifeHours`, default 72h: un evento a esa antigüedad
  pesa la mitad) — los eventos recientes pesan más sin descartar de golpe
  los antiguos dentro de la ventana. Las alertas "duras" (`CAPTCHA`,
  `SUSPENDIDO`, `CAIDO`) pesan 1.5x más que las transitorias (`RATE_LIMIT`,
  `TIMEOUT`, `DESCONOCIDO`) porque indican bloqueo activo del motor, no una
  degradación pasajera.
- Clasificación: `SALUDABLE` (score ≥ 0.85), `INESTABLE` (≥ 0.5),
  `DEGRADADO` (< 0.5) — pero solo si hay peso muestral suficiente
  (`minSampleWeight`, default 3); si no, `SIN_DATOS_SUFICIENTES`. Un engine
  sin ningún evento en la ventana recibe `SIN_DATOS`, **nunca** se asume
  saludable por ausencia de datos. Umbrales documentados inline y
  parametrizables (no hardcoded sin explicación).
- `buildSearchEngineHealthEvents(diagnostico)`: convierte el diagnóstico ya
  calculado por el nodo n8n (`motores_detectados`, `motores_no_responden`)
  en eventos `{component, status, detail}` listos para
  `rhia.system_health_event`. Si un motor aparece exitoso Y en alerta en la
  misma consulta, la alerta prevalece (señal más accionable).

**Pruebas reales**: 13/13 `node --test` en verde, corridas dos veces sobre
el código tal como quedó commiteado en el repo real del usuario (no una
copia): una vía `node --experimental-strip-types` (Node 22 del dispositivo,
sin compilar) para verificación inmediata en esta sesión, y el
`package.json` del paquete deja listo `npm test` (`tsc` + `node --test
dist/*.test.js`) para cuando el toolchain completo del usuario lo compile,
igual que el resto del monorepo. Casos cubiertos: motor 100% sano reciente
→ `SALUDABLE`; mitad fallos transitorios → `INESTABLE` (no `DEGRADADO`,
evita sobrerreaccionar); alertas duras repetidas → `DEGRADADO`; sin
eventos → `SIN_DATOS`; pocos eventos → `SIN_DATOS_SUFICIENTES` aunque todos
sean éxito; eventos fuera de ventana se ignoran; el decaimiento hace que un
fallo reciente pese más que un éxito antiguo y viceversa; componentes que
no son de motor de búsqueda se ignoran.
