## Bug real encontrado y corregido durante este mismo ciclo (documentado, no oculto)

Primera corrida real de `node --test dist/*.test.js` (34/37 pass — luego 35/37 tras un segundo vistazo): la prueba requerida "Timeout" fallaba con `actual: 20` en vez de `'RHIA_WORKFLOW_TIMEOUT'`. Causa real: `runStep` clasificaba un error capturado con un chequeo heuristico ("¿tiene un campo `code`?") para distinguir un `BrowserError` ya construido (lanzado por `assertDomainAllowed`/`resolveTypeValue`) de una excepcion cruda a clasificar. Un `DOMException` real (el `AbortError` que produce un timeout real) TAMBIEN trae un campo `.code` nativo -- el codigo legado numerico DOM4 (`20` para `AbortError`) -- por lo que el chequeo heuristico lo confundia con un `BrowserError` ya clasificado y devolvia el `DOMException` crudo (con su `.code` numerico) en vez de pasarlo por `classifyStepError`. Corregido reemplazando el chequeo heuristico por una clase real dedicada (`ClassifiedBrowserError`, envoltorio explicito con un campo `browserError` real) -- `runStep` ahora solo trata como "ya clasificado" una instancia real de esa clase, cualquier otra cosa (incluido un `DOMException` real) SIEMPRE pasa por `classifyStepError`. Segunda causa real encontrada en la misma corrida: la prueba de redaccion de `SECRET_REF` esperaba la palabra "redactado" en el resumen de evidencia, pero el resumen solo usaba el marcador `••••••` sin esa palabra -- corregido el texto del resumen (`TYPE (valor redactado: ••••••)`), no la prueba (el fallo era real: el mensaje no era suficientemente explicito para un log humano). Ambos fallos se dejan documentados aqui en vez de ocultarse; la corrida FINAL (evidencia de la seccion siguiente) es la que ya incluye ambas correcciones.

## Fuera de alcance de este ciclo (honesto, no oculto)

- **Ningun driver real de Playwright esta conectado.** `BrowserDriver` es una interfaz provider-neutral -- implementarla con Playwright real (lanzar Chromium/Firefox, DOM real) es responsabilidad de un proceso host/worker fuera de este paquete puro, mismo patron que TODOS los hermanos de PH05/PH08/PH09 (ningun proveedor real -- OpenAI, n8n webhook real, calendario real -- esta conectado tampoco). Esto es exactamente el alcance declarado del Handoff del propio packet: "Handoff Computer Use fallback" (`PH09-T003`) asume que este worker existe como CONTRATO, no que ya tiene un navegador real detras.
- **Ningun vault real de secretos esta conectado.** `SecretResolver` es una interfaz -- resolver un `SECRET_REF` a un secreto real es responsabilidad de un caller/infra fuera de este paquete, nunca de este worker.
- **`looksLikeRawSecret` sigue siendo una heuristica, no una garantia** (documentado ya por `PH09-T001`, heredado sin cambios aqui).
- **No hay ninguna tabla real de persistencia para escenarios/ejecuciones/checkpoints en Postgres.** Igual que `tool-registry`, este es un paquete puro sin persistencia -- un checkpoint real que sobreviva un restart del proceso host requeriria una decision de esquema explicita, fuera de alcance de este ciclo.
- **`npm install` no se corrio desde la raiz** (mismo motivo, `device_bash` no disponible) -- el symlink `node_modules/@rhia/playwright-worker` no existe todavia en el toolchain real de Windows; ademas, `@rhia/domain`/`@rhia/policy` NO se reconstruyeron localmente en Windows en este ciclo (solo en el workspace cloud aislado) -- si un ciclo futuro con `device_bash` real corre `npm run build` desde la raiz, deberia confirmar que sigue en verde.
