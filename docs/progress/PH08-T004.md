## Decision de alcance

Igual que `channel-gateway`/`sequence-engine`/`messaging`, este ciclo construye `packages/conversation-agent` (`@rhia/conversation-agent`) como **paquete puro, sin persistencia propia y sin llamar a ningun LLM real** (mismo limite honesto: no hay credencial de AI Gateway autorizada en este ciclo). Depende de `@rhia/outreach-policy` (tipos) y `@rhia/messaging` (`lintMessage`/`renderFactMention`/`ContextPack`, reusados de verdad, no reimplementados).

**Que NO se reimplemento:**
- El policy lint de "no ofrecer descuento / no afirmar dato sin soporte / no urgencia falsa / opt-out presente" vive UNICAMENTE en `@rhia/messaging#lintMessage` -- este paquete lo llama, nunca duplica sus 4 patrones.
- La traduccion de un `Fact` a texto (`renderFactMention`) se reusa tal cual de `@rhia/messaging` para la respuesta de "pregunta de producto" -- ningun modulo nuevo reimplementa esa logica.

**Que SI es nuevo en este ciclo (las 6 acciones del packet):**
1. `intent.ts` -- accion 1 ("Classify intent") y accion 6 ("Detect meeting intent"): clasificador de patrones explicitos (mismo espiritu que `claim-extraction.ts`/`policy-lint.ts`, "mejor pocas reglas explicitas con alta precision que fingir comprension semantica"), con un orden de prioridad documentado (`OPT_OUT`/`HOSTILE` primero por seguridad; `COMMITMENT_REQUEST` antes de `COMMERCIAL_TERMS_REQUEST` porque un pedido de compromiso vinculante puede mencionar "SLA", palabra clave tambien de terminos comerciales -- ADR-011 es la regla mas estricta y gana). `detectMeetingIntent` es una señal INDEPENDIENTE, coexiste con cualquier intencion primaria.
2. `schema.ts` -- `PriceBook`/`PriceBookItem`, tipo plano local (sin zod, mismo patron y misma razon que `Inference` de `messaging/schema.ts`: sin red para instalar zod 4.4.3 real) que refleja 1:1 las tablas reales `price_book`/`price_book_item` YA EXISTENTES -- ninguna tabla ni columna nueva (guardrail del proyecto respetado explicitamente).
3. `price.ts` -- accion 4 ("Comunicar precio oficial"): `communicateOfficialPrice` solo devuelve un precio cuando el `PriceBook` esta `ACTIVE` Y la fecha real cae dentro de `[validFrom, validTo)` -- por construccion, nunca puede comunicar un precio de un price book `DRAFT`/vencido/todavia no vigente (criterio "Precio oficial activo puede comunicarse" + error a evitar "Responder con precio stale", la MISMA funcion resuelve ambos).
4. `escalation.ts` -- accion 5 ("Escalar descuento/commitment"): `ApprovalDraft` (NO un `CreateApproval` real -- le faltan `jobId`/`targetRef`/`idempotencyKey`, que solo puede aportar un caller real conectado a `apps/core-api` con un Job ya existente; mismo tipo de "punto de extension" que ya documento `SequenceMessageBuilder` en `sequence-engine/runner.ts`). `action` mirror exacto (mismos 4 valores literales) del `ApprovalActionSchema` real de `apps/core-api/src/contracts.ts`, `reasonCode` verificado contra el mismo patron regex real.
5. `reply.ts` -- accion 3 ("Responder preguntas permitidas"): 3 constructores de respuesta (escalacion/precio/pregunta de producto), cada uno SIEMPRE anexa una clausula de opt-out real y SIEMPRE se audita con `lintMessage` reusado. Documenta y resuelve explicitamente una tension real descubierta en este ciclo: `lintMessage` fue diseñado para outreach proactivo (mencionar cualquier precio es SIEMPRE violacion) pero este paquete SI tiene un caso legitimo de comunicar precio (ADR-010 lo permite cuando `ACTIVE`) -- `safe` excluye el codigo `PRICE_OR_DISCOUNT` UNICAMENTE cuando la respuesta en efecto comunico un precio oficial real, nunca en otro caso; el resultado COMPLETO del lint (los 4 codigos) siempre se devuelve para trazabilidad, nunca se oculta un issue.
6. `conversation-agent.ts` (`handleInboundMessage`) -- orquesta las 6 acciones en el orden exacto de `PLAN_MAESTRO.md` "F5 -- Conversacion": clasifica, nunca envia una respuesta comercial sin escalar primero (descuento/terminos/commitment SIEMPRE `action: 'ESCALATE'`, nunca `'REPLY'` con confirmacion -- asi se resuelve el criterio "Commitment no aprobado se bloquea": el bloqueo ES la escalacion), comunica precio solo si `PRICE_INQUIRY`, y siempre devuelve `meetingIntentDetected` independiente de la accion tomada.

**Que se deja explicitamente fuera (accion 2, "Retrieve context... y price book aplicable"):** la construccion real del `ContextPack`/`PriceBook` desde Postgres es responsabilidad del CALLER, no de este paquete puro -- mismo limite que ya declararon los 3 hermanos de PH08. `handleInboundMessage` los recibe YA CONSTRUIDOS.

## Fuera de alcance de este ciclo (honesto, no oculto)

- **No hay generacion real via LLM/AI Gateway** para clasificar intencion ni redactar respuestas -- mismo limite que declararon todos los hermanos de PH08 (sin credencial real autorizada en este ciclo). `classifyIntent` es 100% deterministico por patrones.
- **`ApprovalDraft` no es un `CreateApproval` real.** Le faltan `jobId` (de un Job YA EXISTENTE en el tenant, exigido por `ApprovalService.create` real de `apps/core-api`), `targetRef` e `idempotencyKey`. Conectar este paquete a un caller real que arme el `CreateApproval` completo (probablemente un worker o un endpoint nuevo de `apps/core-api` que reciba mensajes entrantes) es wiring de infraestructura futuro, mismo limite que `SequenceMessageBuilder` dejo pendiente en `PH08-T002`.
- **No hay retrieval real de `ContextPack`/`PriceBook` desde Postgres.** Este paquete los recibe ya construidos -- accion 2 del packet ("Retrieve context... y price book aplicable") es responsabilidad de un caller real, no de un paquete puro.
- **No hay agendamiento real de reunion.** `detectMeetingIntent` solo devuelve una señal booleana -- "consultar calendario y agendar" (ultimo paso de "F5 -- Conversacion") es exactamente el alcance de `PH08-T005` (Meeting Scheduler), el handoff explicito de este packet.
- **`npm install` no se corrio desde la raiz.** `device_bash` no estuvo disponible en ningun momento de este ciclo (ver bloqueo de entorno arriba) -- el symlink `node_modules/@rhia/conversation-agent` (y su entrada en `package-lock.json`) que `npm install` generaria normalmente no se creo en el repositorio real; tampoco existe todavia para `@rhia/messaging`/`@rhia/sequence-engine`/`@rhia/channel-gateway` (limitacion heredada, ya documentada por esos 3 ciclos). El paquete se probo de forma real y completa en un workspace aislado del contenedor cloud -- ver "Evidencia real" -- pero una sesion futura con `device_bash`/`npm install` funcionando debe correr `npm install` una vez desde la raiz para que los 4 paquetes nuevos de PH08 queden resueltos tambien por el toolchain real de Windows.
