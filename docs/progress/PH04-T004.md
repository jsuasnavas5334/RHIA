## Objetivo

Dar visibilidad y control seguro sobre jobs y approvals, con contexto humano, idempotencia y políticas Core obligatorias.

## Dependencias verificadas

- `PH04-T001`: Core API v1 `DONE`.
- `PH04-T003`: App shell `DONE`.

## Avance verificable

- Core acepta estados completos de job y expone comandos `POST /api/v1/jobs/:id/retry` y `POST /api/v1/jobs/:id/cancel`.
- Retry solo admite `FAILED`/`PARTIAL`, incrementa una vez, limita a tres intentos y conserva idempotencia.
- Cancel solo admite trabajos aún no iniciados (`PENDING`, `QUEUED`, `RETRY_SCHEDULED`) y elimina cualquier siguiente intento.
- Un job cancelado ya no puede originar nuevas approvals.
- PostgreSQL bloquea la fila por tenant antes de retry, cancel o creación de approval.
- Operations Center muestra jobs, filtros de estado/agente, trazas resumidas e inbox de approvals con motivo, objetivo y solicitante.
- La App dispone de un cliente server-only que reenvía únicamente la cookie opaca `rhia.session_token` al Core, sin confiar roles ni tenant del navegador.
- `GET /api/v1/session` expone exclusivamente roles humanos autenticados; no devuelve IDs de usuario u organización.
- Los formularios de retry, cancel y decisión generan correlación e idempotency keys en servidor y cada mutación vuelve a autorizarse en Core.
- Sin `RHIA_CORE_API_URL`, sesión válida o respuesta íntegra, producción falla cerrada; el modo local conserva datos demostrativos con acciones deshabilitadas.

## Pruebas y evidencia

- Core API: 22/22 pruebas ejecutables aprobaron; dos integraciones condicionales se omiten fuera del gate temporal.
- Retry duplicado mantiene `retry_count=1`, un audit y un registro idempotente.
- Cancel bloquea retry y nuevas approvals, y usuarios sin `jobs.execute` reciben 403.
- Gate PostgreSQL real aprobó siete migrations, integración Core/Auth, datos legacy y segundo restore limpio sobre backup cifrado temporal.
- Web: 17/17 pruebas aprobaron, incluidos cliente Core, validación de sesión, redacción de payloads, correlación, idempotencia y habilitación condicionada de formularios; typecheck y build de producción aprobaron.
- Navegador local: filtro combinado dejó un solo job; dos approvals mostraron contexto y formulario de razón; consola sin errores.
- Smoke HTTP local en puerto aislado: `/jobs` respondió 200, mostró aviso de preview, conservó acciones deshabilitadas y no serializó IDs técnicos demostrativos.
- E2E real sobre restore cifrado temporal: cookie Better Auth → cliente App → HTTP Core → policy → PostgreSQL; approval `PENDING` pasó a `APPROVED` con aprobador humano y un solo audit.
- El gate ahora propaga explícitamente `RHIA_TEST_DATABASE_URL` desde WSL a Node Windows, evitando que integraciones condicionales se omitan silenciosamente.
- Baseline de repositorio: 22 controles sobre 221 archivos publicables, sin mostrar valores sensibles.

## Decisiones

- No ofrecer cancelación de un job `RUNNING` hasta que el worker implemente cancelación cooperativa verificable.
- No ejecutar acciones desde la vista de demostración: cada mutación deberá reautenticar y volver a autorizar en servidor.
- No exponer UUIDs técnicos en las tarjetas; las trazas se resumen con lenguaje operativo.
- No reenviar el header Cookie completo: solo se permite la cookie de sesión RHIA normal o `__Secure-` para evitar filtrar cookies ajenas al Core.
- Los errores de Core se convierten en estados seguros de UI y nunca muestran detalles internos.

## Riesgos residuales

- Falta prueba de cancelación cooperativa del worker; por ello `RUNNING` continúa fuera de los estados cancelables.
- El E2E verifica el cliente exacto invocado por Server Actions y su formulario mediante component test; la navegación con navegador real se ampliará en PH09.
