## Decision de alcance

Paquete puro nuevo `packages/tool-registry` (`@rhia/tool-registry`), sin persistencia real (mismo patron que todos los hermanos de PH08/PH09 anteriores). Depende de `@rhia/policy` (capability model real, reusado) y `@rhia/domain` (declarado como dependencia por consistencia del catalogo de errores, aunque el unico valor literal reusado -- `'RHIA_TOOL_FORBIDDEN'` -- se referencia como string, no como import de tipo, ver "Que SI es nuevo" abajo).

**Que NO se reimplemento:**
- El modelo de capabilities (`capabilityKeys`, `serviceCapabilityCeilings`) vive UNICAMENTE en `@rhia/policy` -- `requiredCapability` de un `ToolManifest` es literalmente un `CapabilityKey` real, validado en runtime contra la lista real (`validateToolManifest`), no un string libre.
- La forma de un registro de salud (`component/status/detail/occurredAt`) sigue el patron real de la tabla YA EXISTENTE `system_health_event` -- no se propone una tabla nueva para esto.

**Que SI es nuevo en este ciclo (las 5 acciones del packet):**
1. `contracts.ts` (acciones 1-3, "Definir tool manifest"/"Registrar capabilities"/"Mapear credentials refs"): `ToolManifest` (`id`, `name`, `ownerRef`, `riskLevel`, `requiredCapability: CapabilityKey`, `credentialRef: string | null`, `allowedDomains`, `allowedActions`) + `validateToolManifest(raw: unknown)` -- validacion REAL en runtime (el input llega como `unknown`, nunca se confia en que ya cumple el tipo TS) que exige `ownerRef`/`riskLevel` (criterio "Cada tool tiene owner y risk"), `requiredCapability` real de `@rhia/policy` y al menos una `allowedAction` (error a evitar "Tools sin policy"), y rechaza un `credentialRef` que "parece" una credencial real (`looksLikeRawSecret`, heuristica declarada como tal -- Bearer/JWT-like/AWS-key-like/cadena larga sin estructura de nombre) -- error a evitar "Pasar credenciales en prompt".
2. `health.ts` (accion 4, "Health check"): `ToolHealthRecord` (alineado a `system_health_event`) + `isToolAvailable` -- fail-closed: `DOWN` y `UNKNOWN` (nunca chequeada) se tratan igual, NO disponible; solo `UP`/`DEGRADED` cuentan como disponible.
3. `registry.ts`: `ToolRegistry` (registro en memoria, rechaza duplicados en silencio) + `listForPrincipal` (criterio "Agent solo ve tools permitidas" -- filtra por capability real + techo real de `@rhia/policy` Y por salud real; un `Principal` `HUMAN` siempre ve la lista vacia, decision de alcance documentada: las tools son un concepto de capability de SERVICIO, el packet dice "permitir a AGENTES operar herramientas").
4. `authorization.ts` (accion 5, "Allowed domains/actions", y "Validacion final": "Runtime rechaza tool fuera de capability"): `authorizeToolInvocation` -- 4 chequeos en orden (capability/techo real -> salud -> accion permitida -> dominio permitido), cada uno con su propio codigo de denegacion (`RHIA_TOOL_FORBIDDEN` reusa el string real de `@rhia/domain`; `RHIA_TOOL_UNAVAILABLE`/`RHIA_TOOL_ACTION_FORBIDDEN`/`RHIA_TOOL_DOMAIN_FORBIDDEN` son locales, mismo patron que `CalendarErrorCode`/`ChannelErrorCode` de los hermanos de PH08 -- ningun otro paquete tiene hoy un codigo real equivalente para esos 3 casos).

## Errores que debe evitar (packet) -- como se evitaron

- "Pasar credenciales en prompt": `ToolManifest.credentialRef` es SOLO una referencia/nombre -- nunca hay un campo para el valor real de una credencial en todo el paquete, y `validateToolManifest` ademas rechaza activamente cualquier valor que "parezca" un secreto real (heuristica declarada, no una garantia matematica -- documentado como tal).
