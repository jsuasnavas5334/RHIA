## Decisión de alcance

Paquete puro nuevo `packages/alerting` (`@rhia/alerting`), mismo patrón
estructural que todos los hermanos de PH09/PH10/PH11. Depende en runtime
real de `@rhia/policy` (dist reusado, 0 cambios) y `@rhia/observability`
(recompilado desde `src/` real este ciclo, 0 cambios).

**Decisión de diseño real más importante:** NO se depende de
`@rhia/model-router` ni de `@rhia/outreach-policy` como paquetes npm reales
en este ciclo, aunque ambos tienen `dist/` committeado y en principio serían
reusables tal cual (sin recompilar). El motivo real: el `.d.ts` de
`@rhia/model-router` (`contracts.d.ts`) re-exporta un `import type {
ProviderId } from "@rhia/ai-gateway"` -- inofensivo en sí mismo (`@rhia/
ai-gateway` no tiene dependencias externas), pero arrastrar el árbol
completo de `@rhia/ai-gateway` (~15 archivos `dist`: gateway, 5 adapters,
transport, testing) solo para poder importar 2 tipos de datos puros
(`BudgetLimits`/`BudgetPeriodUsage`) se evaluó como desproporcionado. Peor
aún, `@rhia/outreach-policy` sí tiene un bloqueo REAL (no solo
desproporción): su `.d.ts` depende tipográficamente de `@rhia/config`, que a
su vez depende de `zod` en runtime -- `zod` NO está disponible ni localmente
ni por red en este contenedor cloud (mismo bloqueo exacto ya documentado
para `@rhia/evidence-pipeline` en `docs/progress/PH10-T003.md`). Se copiaron
textualmente los 2 tipos de datos sin lógica (`BudgetLimits`/
`BudgetPeriodUsage`) y el enum de estados de `TouchLedgerEntry.status`
(`BounceLedgerStatus`) a `packages/alerting/src/fixtures/vendored-types.ts`,
con la justificación completa documentada en ese mismo archivo -- mismo
principio ya aplicado a `claim-extraction.ts` en `PH10-T003` (copiar un tipo/
lógica puro y sin dependencias es preferible a arrastrar un árbol de
dependencias desproporcionado o bloqueado, y siempre preferible a
reinventar la lógica real).

**`docs/runbooks/alerting-runbook.md` es un entregable real nuevo**, no solo
un string de referencia -- cada `Alert.runbookRef` apunta a una sección real
y completa de ese documento (procedimiento de diagnóstico + acción por
categoría), cumpliendo la validación final del packet "Runbook enlazado
desde alerta" con contenido real, no un placeholder.

**Módulos nuevos (mapeados 1:1 a las 6 acciones del packet + dedupe):**

   clave de DEDUPE (estable por condición real, no por ocurrencia).

4. `backup.ts` (acción 3, "Backup stale" / criterio "Age monitor"):
   `evaluateBackupStaleAlerts` sobre un `BackupStatusSignal` real (contrato
   puro -- `PH10-T004` no existe todavía, ver "Fuera de alcance").
5. `budget.ts` (acción 4, "Cost budget" / criterio nombrado "Budget
   hard/soft limits"): `evaluateBudgetAlerts` sobre `BudgetLimits`/
