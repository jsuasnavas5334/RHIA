## Decisiones

- El tenant proviene del principal autenticado, nunca del payload.
- Un replay idempotente no crea un segundo audit event.
- Persistencia real se conectará mediante puertos y deberá usar una transacción única.
- Contacts nacen `UNVERIFIED`; opportunities nacen `DISCOVERED/OPEN` con score cero.
- Services pueden solicitar approvals, pero solo humanos autorizados pueden listarlos o decidirlos.
- Una decisión nunca ejecuta la acción comercial; solo registra estado y audit.
- El transporte nunca deriva el principal de headers del cliente; PH04-T002 proveerá autenticación real.
- Approval, action y job deben coincidir en tenant; el trigger PostgreSQL rechaza divergencias.
- `AsyncLocalStorage` limita el cliente transaccional al flujo asíncrono actual; lecturas fuera de writes usan el pool.

## Riesgos

- Evitar SQL directo desde UI y lógica de negocio duplicada.
- No habilitar acciones comerciales reales ni servicios externos.
