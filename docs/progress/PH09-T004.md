## Decision de alcance

Paquete puro nuevo `packages/skill-library` (`@rhia/skill-library`). Depende de `@rhia/tool-registry` (reusa `ToolManifest`/`looksLikeRawSecret`), `@rhia/playwright-worker` y `@rhia/computer-use` (reusa `Scenario`/`ComputerUseTask` y sus `validateScenario`/`validateTask` reales -- NUNCA reimplementados) y `@rhia/domain` (declarado por consistencia).

**Decision de diseño real encontrada durante la construccion (no anticipada al leer el packet):** el `SkillRunner` necesita delegar la ejecucion del procedimiento a una instancia REAL de `PlaywrightWorker`/`ComputerUseWorker` -- pero para probar eso con evidencia real, un test necesitaria un fake driver de esos paquetes (`FakeBrowserDriver`/`FakeComputerUseDriver`), que NINGUNO de los dos expone fuera de si mismos (`package.json#exports` solo declara `"."`, un import de subpath como `@rhia/playwright-worker/dist/testing/fake-driver.js` fallaria real en runtime con `ERR_PACKAGE_PATH_NOT_EXPORTED`, confirmado antes de intentar escribir un test que dependiera de eso). Se decidio NO modificar los `exports` de esos 2 paquetes ya cerrados (`PH09-T002`/`PH09-T003`) solo para este caso -- en cambio, `SkillRunnerDeps` declara 2 interfaces ESTRUCTURALES minimas propias (`PlaywrightProcedureRunner`/`ComputerUseProcedureRunner`, cada una con solo el metodo `run` real que este paquete necesita) en vez de las clases concretas. Una instancia real de `PlaywrightWorker`/`ComputerUseWorker` SI satisface esas interfaces (tiene ese metodo publico) sin ningun adapter -- y un test puede usar un objeto literal simple (`{ run: async (scenario) => resultado }`) sin necesitar ningun fake interno de esos paquetes. Efecto colateral positivo: acoplamiento mas debil (Skill Library depende de una FORMA, no de una clase concreta).

**Decision de alcance explicita (Prueba "Skill stale"):** `ToolManifest` de `@rhia/tool-registry` no tiene un campo `version` real -- se definio `computeToolContractFingerprint(manifest)` (hash SHA-256 real, no simulado, de `requiredCapability`+`allowedActions`+`allowedDomains` ordenados) como el "version" real e implicito del CONTRATO de una tool. Un `SkillManifest` guarda el fingerprint contra el que fue construido (`builtAgainstToolFingerprint`); `isSkillStale` compara ese valor contra el fingerprint REAL del `ToolManifest` actual, entregado por el caller (nunca cacheado). Deliberadamente el fingerprint IGNORA `ownerRef`/`riskLevel`/`credentialRef` (campos administrativos que pueden cambiar sin invalidar ningun step de ningun skill) -- probado explicitamente (mismo fingerprint con `ownerRef`/`riskLevel` distintos, fingerprint distinto con `allowedActions` distinto).

**Que NO se reimplemento:**
- `validateScenario`/`validateTask` reales -- `validateSkillManifest` DELEGA la validacion de `procedure`/`rollback` a ellos (nunca revalida selectors/domains/secrets por su cuenta) -- esto es lo que garantiza el criterio "No mezcla secretos" para el procedimiento en si, sin duplicar el heuristico `looksLikeRawSecret` (SI se reusa una vez mas, directamente, para los NOMBRES de campos `io.inputs`).
- Ninguna libreria de validacion de schemas externa (zod es devDependency SOLO de la raiz del monorepo, nunca instalada en este workspace cloud aislado sin red) -- `SkillIoSchema` es un esquema minimo propio (`{name, type, required}`), validado a mano, mismo estilo que el resto de PH09.
