## Objetivo

Permitir acceso seguro del equipo interno con login, logout, expiración de sesión, bootstrap administrativo, rate limit y auditoría, cargando roles desde Core.

## Dependencias verificadas

- `PH03-T002`: RBAC y capability policies `DONE`.
- `PH04-T001`: Core API v1 y `PrincipalAuthenticator` `DONE`.

## Criterios de aceptación

- Passwords hasheadas con algoritmo fuerte.
- Session expiry verificable.
- Roles cargados desde Core.
- Login brute-force, expiry y privilege escalation tests aprobados.
- Threat checklist revisada antes del cierre.

## Límites

- No almacenar tokens de sesión en `localStorage`.
- No implementar criptografía ni manejo de passwords desde cero.
- No crear credenciales reales ni activar servicios externos.

## Siguiente paso

Handoff a `PH04-T003`: consumir `createRhiaAuthRuntime().authenticate` y ocultar navegación según los roles del `Principal`.

## Avance verificable

- Better Auth 1.7.1 seleccionado contra documentación oficial y peer dependencies compatibles con `pg`/Drizzle actuales.
- Perfil definido: signup cerrado, sesión opaca de 8 horas, cookies seguras, rate limit persistente y roles desde Core.
- Threat checklist inicial documentada en `docs/architecture/auth.md`.
- Se mantiene `scrypt` de la librería; no se implementará criptografía propia.
- Workspace `@rhia/auth` creado con configuración tipada, sin secrets embebidos.
- Schema mapping oficial validado: cinco tablas auth, signup deshabilitado y campos snake_case.
- Migration `0006_auth_v1` agrega cinco tablas UUID y relación 1:1 `auth_user → app_user`.
- Drizzle actualizado a 51 tablas; paridad y typecheck DB aprobados.
- Better Auth inspeccionó la migration aplicada sin detectar tablas/columnas faltantes ni cambios inseguros.
- Bootstrap del primer administrador implementado como transacción serializada por organización.
- El bootstrap no contiene contraseña predeterminada: exige un hash `scrypt` producido por Better Auth, normaliza email y audita una sola vez.
- Repetir la misma identidad es idempotente; intentar una segunda identidad administrativa queda bloqueado y revierte la transacción.
- El bootstrap solo considera existente un ADMIN activo con cuenta credential y hash; puede reparar únicamente un hash ausente sin sobrescribir uno vigente.
- `PostgresPrincipalResolver` carga `organizationId`, estado y roles desde Core en cada sesión; ignora tenant/roles entregados por el cliente.
- Runtime Auth ensambla Better Auth con el autenticador estructural esperado por Core API.
- Handler HTTP nativo Better Auth queda expuesto con `Cache-Control: no-store`.
- El rate limit usa la IP directa del socket escrita por el adaptador en un header interno, anulando cualquier valor aportado por el cliente.
- Migration `0007_auth_audit` agrega triggers atómicos para login exitoso, revocación y expiración de sesión sin cambiar tablas.
- Fallos de login y respuestas 429 se registran como `system_health_event` con ruta y status, sin email, password, token ni IP.
- La integración HTTP verifica conteos exactos de bootstrap, login, logout/revocación, expiry, fallos y rate limit.
- Drizzle conserva paridad de 51 tablas y avanza su manifest a `0007_auth_audit`.
- 9/9 pruebas locales ejecutables y 4/4 integraciones PostgreSQL/HTTP reales aprobaron.
- Las siete migrations y las cuatro integraciones reales aprobaron sobre restore cifrado temporal; legacy, seeds, constraints y segundo restore limpio permanecieron intactos.
- Login/logout, cookie estricta, expiry, brute force 5/15 min, no enumeración, privilege escalation y eventos de auditoría aprobaron juntos.

## Riesgos

- Ejecutar el bootstrap real debe seguir exigiendo autorización explícita y una contraseña suministrada en tiempo de operación.
- Ningún secret de auth existe todavía; su creación/configuración requiere mantenerlo fuera del repositorio.
- La configuración de proxy/origin depende del deployment y permanece pendiente.
- El secret y la credencial de operación continúan fuera del repositorio y deberán aprovisionarse solo en el entorno autorizado.
