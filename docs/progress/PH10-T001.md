## Decisión de alcance

Paquete puro nuevo `packages/secrets` (`@rhia/secrets`), mismo patrón
estructural que todos los hermanos de PH09 (`tool-registry`,
`playwright-worker`, `computer-use`, `skill-library`). Depende únicamente de
`@rhia/tool-registry` (reusa `looksLikeRawSecret`) -- se decidió NO declarar
`@rhia/domain`/`@rhia/policy` como dependencias solo "por consistencia" (a
diferencia de `skill-library`) porque ningún archivo de este paquete importa
nada de ellos; se prefirió minimizar dependencias reales sobre replicar el
patrón de declaración sin uso.

**Decisión de diseño real más importante (encontrada leyendo el schema antes
de escribir código, no anticipada al leer solo el packet):** "Encrypt
contact points sensibles" NO requiere una tabla ni columnas nuevas --
`contact_point.value_encrypted`/`value_hash` ya existen. El trabajo real de
esta tarea es la FUNCIÓN que produce esos 2 valores: `encryption.ts` define
`encryptContactPointValue`/`decryptContactPointValue` (AES-256-GCM real via
`node:crypto`, autenticado -- una clave incorrecta o un valor alterado
siempre falla explícito, nunca corrompe en silencio) y
`hashContactPointValue`/`contactPointValueMatchesHash` (SHA-256 real,
normalizado a minúsculas/trim antes de hashear para que el mismo email en
distinto casing produzca el mismo `value_hash`, igual objetivo que
`subject_key_hash`). La clave real NUNCA la genera ni la guarda este
paquete -- `EncryptionKeyProvider` es una interfaz inyectable resuelta por
el host en runtime, mismo principio exacto que `SecretResolver` de
`@rhia/playwright-worker` (PH09-T002) para `TypeInput.SECRET_REF`.

**Decisión de alcance explícita ("Secret scanning CI"):** `scripts/
verify-repository-baseline.ps1` ya es un secret-scanning CI real y
funcionando (evaluado en cada gate desde `PH01`) -- no se creó un script
paralelo. Este ciclo NO pudo re-ejecutarlo (requiere PowerShell/Git en
Windows, bloqueado por el mismo `device_bash` caído de todo el ciclo) --
limitación honesta, documentada, no oculta. En su lugar, se agregó una capa
de pruebas reales EN PROCESO (`secret-scan.test.ts`) que cubre la misma
familia de firmas de secretos (AWS/OpenAI/Bearer/JWT) contra las 2 defensas
nuevas de este paquete (`looksLikeRawSecret` reusado + `redactText`),
ejecutable sin depender del entorno Windows.

**Que NO se reimplementó:**
- `looksLikeRawSecret` (heurístico real de `@rhia/tool-registry`) -- usado
  tal cual para validar `SecretReference.ref`, nunca un heurístico paralelo.
- El secret-scanning CI de repositorio (`verify-repository-baseline.ps1`) --
  reusado como evidencia existente, no duplicado.
- El modelo de permisos/policy de rotación (`secrets.rotate`/`ROTATE_SECRET`,
  ya real en `@rhia/policy` desde antes de esta tarea) -- el runbook nuevo
  documenta el procedimiento humano que se apoya en ese modelo existente,
  no inventa uno nuevo.

**Que SÍ es nuevo en este ciclo (las 5 acciones del packet):**
1. `contracts.ts` (acción 1, "Centralizar secret refs" + acción 4 parte
   lógica de "Rotation runbook"): `SecretReference` + `validateSecretReference`
   (delega en `looksLikeRawSecret` real) + `isRotationDue` (pura, determinista,
   nunca toca un valor real -- criterio "Rotation posible").
2. `redaction.ts` (acción 2, "Redact logs"): `redactText` (patrones de
   contenido: Bearer/AWS/OpenAI/JWT/email/teléfono) + `redactValue`

   por contenido -- defensa en 2 capas documentada explícitamente en el
   header del archivo).
3. `encryption.ts` (acción 3, "Encrypt contact points sensibles"): ver
   "Decisión de diseño real" arriba.
4. `docs/security/secrets-rotation-runbook.md` (acción 4, "Rotation
   runbook"): procedimiento humano completo (detectar vencidos -> generar

5. `errors.ts`: `SecretsErrorCode` (4 códigos), mismo patrón que
