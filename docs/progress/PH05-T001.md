## Objetivo

Ejecutar jobs por pasos con estado PostgreSQL, retries limitados, checkpoints idempotentes, lease recuperable y cancelación segura.

## Dependencias verificadas

- `PH04-T001`: Core API v1 `DONE`.
- `PH03-T004`: Policies comerciales `DONE`.

## Avance verificable

- Máquina de estados, ownership por lease, recuperación de crash y fronteras Core/worker documentadas.
- Se decidió `FOR UPDATE SKIP LOCKED` para claims concurrentes y checkpoint único por job/step para no duplicar acciones.
- Retry máximo permanece en tres y `RUNNING` no promete cancelación hasta implementar handshake cooperativo.
- Migration aditiva `0008_agent_runtime` agrega lease completo al job, índice de claim y checkpoints persistentes únicos por job/step.
- El trigger `job_step_tenant_guard` impide vincular checkpoints con organization, job o execution de otro tenant.
- La fábrica `createPostgresCoreRuntime` compone Core y sus servicios PostgreSQL sin duplicar wiring en pruebas o procesos.
- El generador Drizzle ahora incorpora columnas añadidas mediante `ALTER TABLE`; corrigió además siete columnas Core históricas que la paridad anterior omitía.
- Workspace `@rhia/agent-runtime` creado con store PostgreSQL tenant-aware.
- Claim atómico usa `FOR UPDATE SKIP LOCKED`, prioridad estable, lease acotado y un execution attempt único.
- Un lease vencido cierra el execution anterior, consume un retry y permite que otro worker continúe.
- `beginStep` reutiliza checkpoints `SUCCEEDED`; `reserveAction` conserva un action ID e idempotency key estables incluso después de crash.
- Finalización de step/action/job y programación de retry se realizan dentro de transacciones.
- Al agotar tres retries, el job pasa a `DEAD_LETTER` y ya no puede reclamarse.
- `AgentRuntime` resuelve el plan por `job_type`, encadena steps y omite checkpoints ya completados.
- Cada handler recibe el checkpoint ID como idempotency key y, cuando aplica, un action ID reservado de forma estable.
- El heartbeat renueva el lease durante handlers largos; si pierde ownership aborta la señal y evita finalizar o marcar fallo con un lease ajeno.
- Los errores con código RHIA conservan su clasificación y los demás se normalizan; el retry usa backoff exponencial acotado.
- Worker CLI configurable por entorno agregado con pool PostgreSQL, módulo de planes, polling acotado y salida estructurada.
- SIGINT/SIGTERM detienen nuevos claims, esperan el job activo y cierran el pool; el loop expone contadores de resultados.
- Fixture y prueba de integración terminan un proceso durante un step y verifican recuperación del mismo checkpoint/action.

## Pruebas y evidencia

- Migration `0008` aprobó sobre restore cifrado temporal, junto con las siete migrations anteriores y segundo restore limpio.
- Las guardas rechazaron lease parcial y checkpoint cross-tenant.
- Drizzle parity aprobó 52 tablas y todas sus columnas; typecheck de `@rhia/db` aprobó.
- Prueba PostgreSQL real: dos workers concurrentes produjeron un solo claim; recuperación creó attempt 2 y reutilizó el checkpoint/action completado.
- El ciclo de fallos terminó con `retry_count=3`, cuatro executions, dos checkpoints y un único action reservado para el step idempotente.
- Guardas locales rechazan tenant, worker, lease, step, hash, checkpoint, error y backoff inválidos antes de escribir.
- No quedó contenedor temporal y la base activa no fue conectada.
- Pruebas unitarias del runner: happy path, checkpoint reutilizado, retry exponencial y pérdida de heartbeat; 5 pasaron y la integración PostgreSQL quedó omitida fuera del gate como estaba previsto.
- Pruebas del worker: shutdown durante idle y durante job activo; 7 pruebas locales pasaron y 2 integraciones quedaron omitidas sin URL temporal.

- npm mantiene cuatro vulnerabilidades moderadas previamente conocidas; no se aplicó `audit fix --force` por ser un cambio disruptivo fuera de alcance.
