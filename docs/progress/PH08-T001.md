## Decision de alcance

Igual que `@rhia/ai-gateway` y `@rhia/entity-resolver`, este ciclo construye `packages/channel-gateway` (`@rhia/channel-gateway`) como **paquete puro, sin persistencia propia**: define contratos, logica de idempotencia/timeout/normalizacion de errores, y una interfaz `IdempotencyStore` inyectable que un caller real (app/worker) implementa como una capa fina sobre `core_idempotency` via Drizzle. El paquete no inserta en Postgres el mismo -- ese wiring de persistencia real (y el primer caller real en `apps/core-api`/worker) queda fuera de alcance de este ciclo, misma razon documentada en `PH07-T004`/`PH07-T005`: no existe hoy ningun caller real que aporte datos genuinos (una cuenta de email o WhatsApp real conectada) sin inventarlos.

**Que adapter construir primero** (accion 2, "Implementar primero proveedores disponibles"): no hay ninguna cuenta de proveedor de email/WhatsApp/LinkedIn real configurada en el repo (`PLAN_MAESTRO.md` los describe como "configurable"/"autorizado", es decir, decisiones de negocio pendientes). El unico proveedor real y operativo hoy es n8n (ADR-003, ya usado en produccion segun el baseline de `PH01`). Se construyo un unico adapter de referencia, `n8n-webhook`, que envia via un webhook HTTP de n8n -- agnostico de canal, n8n decide del lado de su propio workflow a que proveedor concreto de cada canal enrutar. Cuando el negocio decida un proveedor especifico (p.ej. un proveedor de email directo, sin pasar por n8n), se agrega como un adapter nuevo implementando `ChannelProviderAdapter`, sin tocar el Gateway ni los contratos -- ese es precisamente el punto de la arquitectura de adapters que pide el Objetivo del packet. El contrato HTTP exacto que ese webhook de n8n deberia implementar (peticion/respuesta) se documento en el codigo (`adapters/n8n-webhook.ts`) porque el workflow de n8n que lo implemente todavia no existe -- es trabajo de integracion posterior.

## Que se construyo

Paquete nuevo `packages/channel-gateway` (`@rhia/channel-gateway`), hermano de `packages/ai-gateway`. Sin dependencias de otros paquetes del monorepo (evita el problema de symlinks de workspace rotos en Windows/`device_bash` que documentaron ciclos anteriores para paquetes con dependencias cruzadas).

- `contracts.ts`: `ChannelId` (`email`/`whatsapp`/`linkedin`/`form`/`chat`/`social`, los 6 canales del Objetivo del packet); `ChannelSendRequest` (incluye `idempotencyKey` obligatorio); `ChannelSendResult` (`SUCCEEDED`/`FAILED`); `ChannelDeliveryStatus` normalizado (`QUEUED`/`SENT`/`DELIVERED`/`READ`/`BOUNCED`/`FAILED`) -- accion 1 y criterio "Delivery status normalizado"; `ChannelErrorCode` (10 codigos, incluye `RHIA_CHANNEL_IDEMPOTENCY_CONFLICT`); `ChannelWebhookEvent`/`ChannelWebhookResult` para la ingesta de callbacks (accion 4).
- `errors.ts`: `createChannelError`, `normalizeUnexpectedError` (nunca deja escapar el objeto de error crudo del adapter, podria traer tokens/headers del proveedor), `isRetryableCode`, `isAbortError` -- mismo patron que `@rhia/ai-gateway/errors.ts`.
- `transport.ts`: `Transport` inyectable + `FetchTransport` real -- ningun adapter llama `fetch` directamente.
- `idempotency.ts` (accion 3 + criterio "Retry no duplica"): `computeSendFingerprint`/`stableFingerprint` (sha256 hex determinista, mismo patron que `excerpt-hash.ts` de `@rhia/evidence-pipeline`); interfaz `IdempotencyStore` (`get`/`record`) mapeada 1:1 sobre las columnas de `core_idempotency` (tabla EXISTENTE, reusada, ninguna tabla nueva); `InMemoryIdempotencyStore` para pruebas/desarrollo local (documentado explicitamente como no apto para produccion). Decision de diseno explicita y documentada en el codigo: solo se registra un envio `SUCCEEDED` -- un `FAILED` (timeout, rate limit, auth) NO se registra, para que un retry real pueda reintentar de verdad contra el proveedor en vez de quedar bloqueado por un intento que nunca llego a confirmarse.
- `adapters/types.ts`: interfaz `ChannelProviderAdapter` (`send`, `parseWebhookEvent`, `capabilities`) que cualquier adapter de canal futuro implementa.
- `adapters/n8n-webhook.ts` (accion 2, adapter de referencia): `createN8nWebhookAdapter` -- normaliza 401/403 -> `AUTH_FAILED`, 429 -> `RATE_LIMITED` (retryable), 5xx -> `PROVIDER_UNAVAILABLE` (retryable), otros 4xx -> `REJECTED` (no retryable), 2xx sin `providerMessageId` -> `UNEXPECTED_FAILURE`, excepcion de transporte (incluye timeout via `AbortError`) -> normalizada, nunca re-lanzada. `parseWebhookEvent` traduce el payload crudo del webhook a `ChannelWebhookEvent`, exige `providerEventId`+`providerMessageId` (Errores a evitar "Ignorar provider IDs").
- `gateway.ts` (`ChannelGateway`, orquestador -- accion 1 + accion 4 + criterios "Provider ack registrado"/"Retry no duplica"): `.send()` resuelve el adapter por `provider`, valida que soporte el `channel` pedido, calcula el fingerprint, consulta `IdempotencyStore.get()` -- si existe con el MISMO fingerprint devuelve el resultado guardado con `deduplicated: true` sin tocar el adapter; si existe con un fingerprint DISTINTO devuelve `RHIA_CHANNEL_IDEMPOTENCY_CONFLICT` (reuso indebido de la key); si no existe, invoca al adapter bajo un timeout real (mismo mecanismo `AbortController`+`setTimeout` que `AiGateway.invoke`) y, solo si el resultado es `SUCCEEDED`, lo registra. `.handleWebhookEvent()` (accion 4, "Delivery callbacks"): parsea el evento via el adapter y deduplica por `providerEventId` dentro de un namespace de operacion por proveedor -- un evento reentregado por el proveedor (comportamiento normal de casi todo sistema de webhooks) se procesa una sola vez.
- `testing/fake-transport.ts`: mismo `FakeTransport` (`respond`/`throw`/`hang`) que `@rhia/ai-gateway/testing`, sin dependencia cruzada -- copia local intencional (paquete sin dependencias).
- `index.ts`: barrel export.

## Errores que debe evitar (packet) -- como se evitaron

- "Enviar directamente desde n8n sin ledger": el unico punto de entrada documentado para enviar es `ChannelGateway.send()`, que SIEMPRE pasa por el chequeo de `IdempotencyStore` (el ledger) antes de invocar al adapter -- no existe ningun camino en este paquete que llame a un adapter sin pasar primero por el Gateway.
- "Ignorar provider IDs": `providerMessageId` es obligatorio en un envio exitoso y `providerEventId` es obligatorio para procesar un webhook -- ambos se validan explicitamente y el adapter lanza/falla si faltan.

## Fuera de alcance de este ciclo (honesto, no oculto)

- **No hay implementacion real de `IdempotencyStore` contra `core_idempotency`.** Solo existe la interfaz (`idempotency.ts`) y `InMemoryIdempotencyStore` para pruebas/desarrollo. La implementacion real via Drizzle (INSERT/SELECT reales sobre Postgres) es trabajo de wiring en la app/worker, mismo limite que `PH07-T004`/`PH07-T005` documentaron para sus propios motores puros.
- **No hay ningun caller real todavia** (ni en `apps/core-api` ni en un worker) que invoque `ChannelGateway.send()` con datos de un prospecto real. Este ciclo entrega el motor, no la integracion end-to-end.
- **Solo existe un adapter (`n8n-webhook`)**, agnostico de canal. No hay adapters especificos de un proveedor de email o de WhatsApp Business API porque esas cuentas/credenciales no existen todavia en el proyecto (`PLAN_MAESTRO.md` las describe como decisiones de negocio pendientes: "Email provider configurable", "WhatsApp Business API/provider autorizado"). El contrato HTTP que el workflow de n8n necesitaria implementar para que este adapter funcione de verdad esta documentado en `adapters/n8n-webhook.ts`, pero ese workflow de n8n en si mismo no se construyo (no es parte del alcance de un paquete puro de TypeScript).
- **No hay UI ni endpoint HTTP real que reciba el webhook entrante** -- `ChannelGateway.handleWebhookEvent()` es la funcion que un endpoint real invocaria con el payload ya parseado del request, pero ese endpoint (en `apps/core-api` o un worker) no se construyo en este ciclo.
