## Decision de alcance

Igual que `@rhia/ai-gateway`, `@rhia/entity-resolver` y `@rhia/channel-gateway`, este ciclo construye `packages/sequence-engine` (`@rhia/sequence-engine`) como **paquete puro, sin persistencia propia**, hermano de `packages/outreach-policy` y `packages/channel-gateway`. A diferencia de `channel-gateway` (que evito deliberadamente dependencias cruzadas de workspace), este paquete SI depende de `@rhia/outreach-policy` (accion "Contexto necesario: OutreachPolicy" del propio packet lo exige) y de los TIPOS de `@rhia/channel-gateway` -- ese es precisamente el punto: Sequence Engine es la pieza que conecta ambos motores ya cerrados, sin duplicar la logica de ninguno.

**Que NO se reimplemento (evita el error "Crear secuencia nueva para evadir limite" heredado de PH03-T003):** el calculo de max toques, stop signals/suppression, cadencia 0/3/7 y channel mix vive UNICAMENTE en `@rhia/outreach-policy#planNextTouch`. Ningun modulo de `sequence-engine` reimplementa esa decision -- `touch-plan.ts` y `runner.ts` la orquestan hacia adelante (preview de varios toques, y avance real toque-a-toque respectivamente) pero SIEMPRE delegando el calculo de "cual es el siguiente toque legitimo o el motivo de parada" a `planNextTouch`, sobre el `context.ledger` REAL que entrega el caller -- nunca un ledger vacio fabricado para saltarse el limite.

**Que SI es nuevo en este ciclo:**
1. `holidays.ts` -- accion 5 del packet ("Reschedule por feriados/ventanas si se configura"), la unica accion que `OutreachPolicy` (PH03-T003) no cubria: un calendario de feriados opcional (`HolidayCalendar`, lista de fechas `YYYY-MM-DD`) que, si se configura, empuja `plannedAt` hacia adelante (nunca hacia atras, para no romper el espaciado minimo entre toques ya calculado) hasta la siguiente ventana habil real que tampoco sea feriado. Reusa `isWithinContactWindow` de `@rhia/outreach-policy` (exportada) en vez de reimplementar la logica de ventana/fin de semana.
2. `touch-plan.ts` -- accion 1 ("Crear touch plan"): una vista previa de SOLO LECTURA de los hasta `maxProactiveTouches` toques restantes de una secuencia (simula el ledger internamente, nunca lo persiste ni lo devuelve), util para mostrar/programar el plan completo en vez de solo el siguiente paso. Documentado explicitamente como preview -- el avance real y el conteo real contra el limite pasan siempre por `runner.ts`/`planNextTouch` sobre el ledger real.
3. `runner.ts` (`advanceSequence`) -- el punto de integracion real con Channel Gateway que el comentario de cierre de `PH08-T001` dejo pendiente: dado el siguiente toque ya calculado (con reschedule de feriados aplicado), resuelve el `provider` del canal (`ChannelProviderResolver` inyectado, p.ej. `() => 'n8n-webhook'`), arma un `ChannelSendRequest` normalizado (mapeo exhaustivo `OutreachChannel` -> `ChannelId` via `toChannelId`, con `never` en el `default` para que un canal nuevo sin mapear sea error de compilacion) y lo entrega a una funcion `send` inyectada (misma inversion de dependencias que `ChannelGateway` usa para `Transport` -- nunca construye un `ChannelGateway` real aqui, ese wiring de infraestructura es responsabilidad de un caller/app real). Si el toque planificado todavia no llega (`now < plannedAt`), devuelve `DEFERRED` sin enviar.

## Fuera de alcance de este ciclo (honesto, no oculto)

- **No hay ningun caller real todavia** (ni en `apps/core-api` ni un worker) que invoque `advanceSequence` con un `ChannelGateway` real conectado a Postgres/n8n. Este ciclo entrega el motor de orquestacion, no el wiring de infraestructura -- mismo limite que declaro `PH08-T001` para si mismo.

- **El `ChannelProviderResolver`/`SequenceMessageBuilder` son inyectados, no implementados aqui.** Este ciclo no decide con que copy real se arma el mensaje de cada toque (eso es PH08-T003, "Implementar generacion y revision de mensajes", que depende explicitamente de este) ni que provider real mapea cada canal en produccion -- solo define el punto de extension tipado para que un caller real los provea.
- **El workspace npm real (`npm install` desde la raiz) no se ejecuto.** `device_bash` no estuvo disponible en ningun momento de este ciclo (ver bloqueo de entorno arriba), asi que el symlink `node_modules/@rhia/sequence-engine` (y su entrada en `package-lock.json`) que `npm install` generaria normalmente no se creo en el repositorio real. El paquete se probo de forma real y completa en un workspace aislado del contenedor cloud (con los `dist/` reales de sus dependencias, sin fabricar ninguno) -- ver "Evidencia real" -- pero una sesion futura con `device_bash`/`npm install` funcionando debe correr `npm install` una vez desde la raiz para que `packages/sequence-engine` quede resuelto tambien por el toolchain real de Windows (`npm run build --workspace=@rhia/sequence-engine`), igual que ya sucede con el resto de paquetes del monorepo.
